In an event-driven microservices architecture where each service maintains its own private database, services keep local copies (projections) of facts owned by other services by consuming domain events from RabbitMQ. In this proof-of-concept, the shared consumer implementation ([`Consumer`](file:///mnt/c/Users/gaura/Documents/GitHub/pf-life-wt-p230-inv/packages/common-persistence/epfo_persistence/consumer.py#L35-L93)) sets a prefetch count of 10 (`prefetch_count=10`) and, whenever a handler raises an unhandled exception, re-publishes the failed message to the back of the queue with an incremented `x-attempts` header before acknowledging it. As a result, events relating to the very same aggregate or record can easily be processed concurrently or out of order. A concrete incident in this system demonstrated the hazard: `compliance-service` received an initial demand event followed by a withdrawal, but concurrent processing and retry re-queuing caused an earlier event to be applied after the withdrawal, leaving a withdrawn Section 7A demand stuck in the `OPEN` state. To safeguard integrity across asynchronous delivery, every local copy must be classified and protected against out-of-order writes, especially when events regarding a single aggregate originate from more than one producer service.

## Needs Per-Copy Protection

When a local projection follows a **last-writer-wins** strategy and events concerning the **same aggregate record originate from more than one producer**, per-producer FIFO ordering (e.g., standard RabbitMQ message routing or partition keys) **cannot** protect the copy against race conditions and out-of-order writes. The consumers run concurrently with prefetch count up to 10 and re-queue failed attempts, meaning messages from disparate producers arrive through independent queues and timings without a global coordinator.

The following eight copies require explicit protection (such as optimistic concurrency control, monotonic event timestamp guards `occurred_at`, state machine transition preconditions, or CRDT-style field separation):

### 1. `claim-service` — `claims` Table (`state`, `recommended`, `prior_state`)
* **Aggregate Record**: `claim_id`
* **Producers**:
  * `member-service` (`AccountFrozen.v1`, `AccountDefrozen.v1`, `MemberExitMarked.v1`, `MemberDeathRecorded.v1`)
  * `workflow-service` (`CaseDecisionSubmitted.v1`)
  * `payment-simulator` (`PaymentConfirmed.v1`, `PaymentReturned.v1`)
* **Failure Scenario**: An `AccountFrozen.v1` event emitted by `member-service` races with an approver's `CaseDecisionSubmitted.v1` (`APPROVED`) from `workflow-service` or a bank settlement `PaymentConfirmed.v1` (`SETTLED`) from `payment-simulator`. If `AccountDefrozen.v1` or an out-of-order decision arrives after payment has been completed, the terminal `SETTLED` state can be reverted to `UNDER_REVIEW` or `AUTO_APPROVED`, leading to duplicate disbursements or contradictory lifecycle statuses.
* **Recommended Protection**: Guard state transitions with monotonic sequence or event timestamp checks (`source_at <= occurred_at`), or enforce strict state machine guards rejecting transitions once a claim enters terminal states (`SETTLED`, `REJECTED`, `REJECTED_WITH_REASON`).

### 2. `contribution-service` — `demands` Table (`state`, `settled_by`, `realised_paise`)
* **Aggregate Record**: `demand_id`
* **Producers**:
  * `compliance-service` (`DemandRaised.v1` [VISHWAS waiver/withdrawal], `RecoveryRealised.v1`)
  * `payment-simulator` (`PaymentConfirmed.v1` [purpose=`DEMAND`])
* **Failure Scenario**: A demand covered under a Section 7A or VISHWAS settlement is marked `WAIVED` or `WITHDRAWN` by `compliance-service.DemandRaised.v1`. Concurrently, an employer direct payment instruction is settled by the bank via `payment-simulator.PaymentConfirmed.v1`. Because the events travel across independent queues, an older payment confirmation can overwrite a waived demand to `PAID`, or a late waiver can mark an already collected demand `WAIVED`, resulting in accounting imbalances between the cash ledger and demand registers.
* **Recommended Protection**: Adopt the monotonic timestamp guard already implemented in `compliance-service` ([`messaging.py:43-45`](file:///mnt/c/Users/gaura/Documents/GitHub/pf-life-wt-p230-inv/services/compliance-service/app/infra/messaging.py#L43-L45)): `WHERE demand_id = :d AND (source_at IS NULL OR source_at <= :occurred_at)`.

### 3. `member-service` — `members` Table (`account_state`)
* **Aggregate Record**: `uan`
* **Producers**:
  * `workflow-service` (`ProcessTransitioned.v1` for `process == "member_freeze"`)
  * `platform-service` (`IssueTrackerExecuted.v1` for administrative actions `FREEZE_MEMBER` and `DEFREEZE_MEMBER`)
* **Failure Scenario**: An urgent administrative defreeze order executed by the IS Division via `platform-service.IssueTrackerExecuted.v1` unfreezes an account (`account_state = 'ACTIVE'`). Meanwhile, a delayed or retried message from an earlier workflow freeze case (`workflow-service.ProcessTransitioned.v1`) reaches `member-service` and overwrites `account_state = 'FROZEN'`, silently undoing the official administrative order.
* **Recommended Protection**: Introduce an `account_state_updated_at` column on `members` and update only when `occurred_at >= account_state_updated_at`.

### 4. `workflow-service` — `cases` Table (`state`, `current_role`, `step`)
* **Aggregate Record**: `claim_id` / `case_id`
* **Producers**:
  * `claim-service` (`ClaimDecisionRecorded.v1`, `PaymentInstructed.v1`, `ClaimStateChanged.v1`)
  * `payment-simulator` (`PaymentConfirmed.v1`, `PaymentReturned.v1`)
* **Failure Scenario**: `workflow-service` tracks case tasks for cashiers and approvers. When `claim-service` emits `ClaimStateChanged.v1` (e.g., redisbursement review or hold transitions), it races with bank confirmations (`PaymentConfirmed.v1` / `PaymentReturned.v1`) from `payment-simulator`. An out-of-order hold event can overwrite a closed case (`CLOSED`) back to `ON_HOLD` or `IN_REVIEW`, corrupting office task queues.
* **Recommended Protection**: Ensure optimistic lock checks (`version = cases.c.version + 1`) reject backwards transitions from terminal states (`CLOSED`), and enforce that `PaymentConfirmed.v1` cannot be superseded by lifecycle events with earlier timestamps.

### 5. `reporting-service` — `claim_facts` Read-Model Table (`decided_at`, `decision`, `settled_at`, `returned_count`)
* **Aggregate Record**: `claim_id`
* **Producers**:
  * `claim-service` (`ClaimSubmitted.v1`, `ClaimDecisionRecorded.v1`)
  * `payment-simulator` (`PaymentConfirmed.v1`, `PaymentReturned.v1`)
* **Failure Scenario**: `reporting-service` aggregates read models for public statistics and zone dashboards. If `payment-simulator.PaymentConfirmed.v1` is consumed before `claim-service.ClaimSubmitted.v1` has created the `claim_facts` row, the update matches zero rows. When `ClaimSubmitted.v1` is subsequently processed, it inserts the row with `settled_at = NULL`. The settled timestamp is permanently lost from the read model, skewing SLA and settlement metrics.
* **Recommended Protection**: Upsert (insert with partial fields on conflict do update) across all handlers updating `claim_facts`, rather than assuming the row was already inserted by `ClaimSubmitted.v1`.

### 6. `reporting-service` — `contribution_facts` Read-Model Table (`wage_month`, `trrn`, `total_paise`, `submitted_at`, `paid_at`, `posted_at`)
* **Aggregate Record**: `filing_id` / `trrn`
* **Producers**:
  * `contribution-service` (`ECRValidated.v1`, `ECRSubmitted.v1`, `ContributionPosted.v1`)
  * `payment-simulator` (`PaymentConfirmed.v1`)
* **Failure Scenario**: `PaymentConfirmed.v1` queries `contribution_facts` by `trrn` to mark `paid_at`. If `PaymentConfirmed.v1` arrives before `contribution-service.ECRSubmitted.v1` (which supplies the `trrn`), the lookup finds no row and the update does nothing. When `ECRSubmitted.v1` subsequently inserts the row, `paid_at` remains `NULL`, causing dashboard reports to show paid returns as unpaid.
* **Recommended Protection**: Key `contribution_facts` on `filing_id` across all events or maintain a deferred staging table for early payment receipts that resolve once `ECRSubmitted.v1` arrives.

### 7. `contribution-service` — `transfer_legs` Table (`detail` JSON column and leg states)
* **Aggregate Record**: `transfer_id`
* **Producers**:
  * `claim-service` (`TrustAnnexureKReconciled.v1`)
  * `pension-service` (`EpsServiceTransferred.v1`)
* **Failure Scenario**: Both handlers update the same row in `transfer_legs` for a Form 13 transfer. Each handler fetches the current `detail` JSON column into Python memory, updates its respective keys (`service_from`/`service_to` vs `service_months`/`breaks_months`), and writes the entire JSON blob back to the database. If both events execute concurrently, the second writer overwrites the changes made by the first, corrupting service history details needed for pension calculations.
* **Recommended Protection**: Use row-level locking (`SELECT ... FOR UPDATE`), database-level JSON patch updates (e.g. `jsonb_set` in PostgreSQL), or separate the PF detail and EPS detail into distinct database columns.

### 8. `intelligence-service` — `claim_facts` Table (`decisions` JSON array)
* **Aggregate Record**: `claim_id`
* **Producers**:
  * `claim-service` (`ClaimSubmitted.v1`)
  * `workflow-service` (`CaseDecisionSubmitted.v1`)
* **Failure Scenario**: `on_case_decision` in `intelligence-service` executes `SELECT decisions FROM claim_facts WHERE claim_id = :id`. If `workflow-service.CaseDecisionSubmitted.v1` arrives before `claim-service.ClaimSubmitted.v1` has created the claim fact row, the query returns `None` and the decision is silently dropped. When `ClaimSubmitted.v1` subsequently arrives, it initializes `decisions = []`, completely missing earlier approver notes and recommendations required for AI scrutiny models.
* **Recommended Protection**: If `claim_facts` row is not yet found, insert a stub record with the decision, or re-raise `LookupError` so RabbitMQ retries the event until `ClaimSubmitted.v1` has established the aggregate.
